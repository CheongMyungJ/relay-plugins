# Relay kb

Read [workflow](../../references/workflow.md), the [knowledge base contract](../../references/kb.md) and the [KB write contract](../../references/kb-write.md). Resolve resource paths relative to this installed SKILL.md, not the user's cwd. Use the `kb` helper command from the invocation repository.

Require a positive PR number first, then optional `--watch`, `--pr` (merged PRs only: record through a small PR instead of pushing to the default branch), `--lang <language>` and natural-language context. The number is a PR, not a Relay issue. An open PR receives one KB commit on its own branch; a merged PR is recorded on the remote default-branch tip. `resume_required` names an unfinished request on that PR; resume it rather than starting another. State lives in `.relay/kb/pr/<n>/<request_id>/`.

Five steps. (1) `inspect {raw:"26 --pr --watch"}` collects and returns `request_id`, `request_hash`, `mode` (open, merged-direct, merged-pr), `source_pr_head`, `apply_base_sha`, `diff_paths`, a bounded `kb` summary, `scope` (existing entries overlapping the diff with auto/judge/broken verdicts), linked issue document names and run IDs, and comment keys. Read the saved snapshot through `inspect {request_id, pr, section, cursor}` pages, never re-collecting: `summary` (PR body, linked issue bodies, Relay documents and implementation reports with their `issue:n/comment:id` sources), `sources` (general and inline comments and review bodies with their source strings, then the diff) and `entries` (scope entries in full). (2) Write candidates in the entry JSON of the write contract with the two attachment lines, typed sources and 2-5 terms; put candidates you cannot support in `rejected` with a reason. (3) `prepare {pr, request_id, request_hash, changes_file, next_step}` runs the gates; classify a `candidates` result in `classified`, resolve a `capacity_resolution_required` result with operations on the listed entries, and prepare again. Otherwise it returns `hash`, review and diff paths, issued IDs and `no_change`. (4) Handle every judge/broken scope entry with update, supersede, absorb, delete or (judge only) reconfirm with evidence; compat entries always need evidence. (5) Show the whole review.md (verdict line, adopted with attachment lines, reconfirmation, rejected, human checks, planned files and the exact KB diff), incorporate feedback with a new prepare, and publish only the exact approved hash with the approving user.

`publish {pr, request_id, hash, approved: true, user, worktree?}` returns `authorized` until a clean connected worktree on a separate local branch at `apply_base_sha` is given; create it, then publish again with `worktree`. The helper rechecks the PR and every cited source (a source of this PR revised since inspection is `stale`), applies, commits `kb: record PR #<n>` with knowledge paths only, pushes, creates the small PR when `--pr` (`<!-- relay:kb-pr <request_id> -->`), and posts one result comment ending with `<!-- relay:kb <request_id> -->` after the rendered next step. An open PR whose head moved stops with `head_advanced` and the observed head; inspect the new commits, `prepare {pr, request_id, publish_only: true, next_step}`, obtain approval of that candidate and publish again. Do not run a review code application push and a kb publication on the same PR at the same time.

Verdict phrases: open PR "KB 커밋 <sha>: 부모 <source_pr_head>, 지식 경로만 포함"; merged PR "KB 커밋 <sha>: 적용 기준 기본 브랜치 <apply_base_sha>, 지식 경로만 포함"; nothing adopted "KB 파일 변경 없음". The next step is null for an open PR or a direct default-branch record and review only when a small PR was created. Report `commit`, `remote_sha`, `comment_url`, `small_pr`, `verdict`, `watch`, `watch_small_pr` and any uncertain stage.

Before choosing `next_step` for any outcome, read [the common next-step contract](../../references/next-step.md) and follow it.
