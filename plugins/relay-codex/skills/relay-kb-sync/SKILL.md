# Relay kb-sync

Read [workflow](../../references/workflow.md), the [knowledge base contract](../../references/kb.md) and the [KB write contract](../../references/kb-write.md). Resolve resource paths relative to this installed SKILL.md, not the user's cwd. Use the `kb` helper command from the invocation repository.

Accept repository-relative paths (extraction), `--limit <n>`, `--branch <name>`, `--resume <run_id>`, `--handoff <round>` and `--watch`; no paths means refresh of every active entry. `--resume` cannot combine with paths or `--branch`; `--handoff` requires `--resume`. This invocation authorizes KB reads and writes, commits (including the run's single empty start commit), pushes, draft PR creation, handoff comments on that PR and closing it when the run ends without changes, all on a task branch; nothing is written to the default branch. Honor later user holds and host permissions. State lives in `.relay/kb/sync/<run_id>/`.

`begin {raw:"scripts/relay_core dispatcher --limit 20 --watch"}` pins the remote default-branch tip as `base_sha`, the branch `relay/kb-<run_id>` (unless `--branch`), the sibling worktree `<root>-relay-kb-<run_id>` and the run's initial limit (`--limit`, otherwise 60 files or 80 entries), and returns `targets`, `auto` and the first `listing` page (later pages through `next_request`; a file too large for one page arrives in `part`s): for extraction the tracked files with sizes, Python symbols, internal imports and the PR/issue numbers from their recent commits; for refresh the judge/broken entries with reasons, while auto entries are recorded locally only. Read further pages with `batch {run_id, list: true, cursor}`.

Choose an order, then `batch {run_id, files[] | ids[], symbols?}` with at most 15 direct files of one directory or 15 entries within the remaining budget; the helper fixes the batch, its scope and starting HEAD and returns symbol fragments (continue through `next_request`). Write the change set for that batch and `checkpoint {run_id, batch_id, changes_file, label?}`: gates against `base_sha` (a `candidates` or `capacity_resolution_required` result leaves the batch open to fix and checkpoint again), apply, commit on the batch's starting HEAD with `kb-sync: <mode> batch <batch_id> (<run_id>)`, push, record the batch's targets and budget once, then create the draft PR after the first real commit or update its body; a batch without tracked changes records its rejections only. Extraction candidates cite `path:<p>@<base_sha>` or the classified PR/issue numbers, never reasons inferred from code. Every call, first or resumed, processes at most the initial limit; never continue past it in the same call.

When a checkpoint reaches the limit with targets left the run is `paused` and the helper hands off: if the run has no PR yet it makes one empty commit on `base_sha`, pushes it and creates the draft PR (watch label and assignee with `--watch`), brings the PR body up to date, then posts a handoff comment ending in the rendered next step (`kb-sync`) and `<!-- relay:kb-sync-handoff {"limit":…,"round":…,"run_id":…,"schema":1,"state":"paused"} -->`. A no-change round on an existing PR adds only its comment. Once the checkpoint result shows the posted handoff, report and end this call; do not batch again. If posting failed, `handoff {run_id}` completes it without repeating the PR or empty commit. The PR body names the run and protocol (`<!-- relay:kb-sync <run_id> handoff:1 -->`) and carries no next step.

When the limit is reached with targets remaining, only complete or recover the handoff publication and report the result, then end the current AI session's work on this run. Never call `resume`, `begin --resume`, or invoke kb-sync again in that same AI session to reset the budget, with or without `--handoff`. A new helper command or skill invocation within the same AI session is not a new session. `next: kb-sync` is a signal for the dispatcher to start a new AI session, not an instruction for the current AI to execute another step. If handoff publication cannot be recovered, report the failure and end without resuming the run.

A new AI session continues the run with `--resume <run_id>`: the dispatcher passes `--limit <initial limit> --handoff <round>` from the handoff comment, and the helper checks the run, round, limit, branch, worktree and open PR, consumes that round once and grants one budget of the initial limit. A result `handoff_consumed` means the round was already used: report it and end without batches. A manual `--resume` (or `resume {run_id}`) in a new AI session without `--handoff` completes an unposted handoff first, consumes the latest round and continues; a different `--limit` is refused. A run from before handoffs restores its initial limit only while still on its first call; otherwise resume it once with an explicit `--limit`.

`finish {run_id}` requires no open batch, no remaining target and a handling operation for every judge/broken entry, and saves `finishing` before any remote step. With a PR whose branch content differs from `base_sha`, it finalizes the body (under 65,000 characters by summarizing counts), marks the PR ready, confirms it and then posts a `finished` handoff suggesting review. With only the empty start commit it posts a `finished` handoff with null and closes the PR without merging. Without a PR it finishes with null and writes nothing. `finished` is saved only after these steps; calling `finish` again completes whatever is missing. Subagents may read fragments and draft candidates; batches, checkpoints and remote writes stay in this session.

Report the run ID, branch, worktree, base SHA, processed and remaining counts, commits and the empty start commit, PR URL, handoff comment URL and round, and `watch` result. Never recreate a missing worktree, force-push, or repost an uncertain PR, close or comment write; resume and finish reconcile it.

Before choosing `next_step` for any outcome, read [the common next-step contract](../../references/next-step.md) and follow it.
